# 本番データの保護

**本番データを壊す事故は、悪意ではなく「接続先を間違えたまま普段どおりの操作をした」ときに起きる。** 本ルールは、本番を書き換え得るすべての経路に共通の下限を定める。

**本プロジェクトの本番 DB は他プロジェクトと共用の Supabase である**（`database.md`「`schema.prisma` に他プロジェクトのモデルが含まれる」）。破壊的操作は `BookRecord*` に留まらず、`Exercise*` / `Report*` / `Video*` を巻き込む。被害範囲が本プロジェクトの外へ及ぶ前提で扱う。

## 原則

- **本番 DB は書き換えない。** 検証・調査・データ操作を伴う作業は、**本番以外の環境**で行う。「本番でしか再現しない」と判断する前に、非本番環境で再現を試みる。
- **書き換えが必要なら、まず環境を分ける**（次節）。本番を対象にするのは、非本番では成立しない運用作業（実データの是正など）に限り、後述の例外手順を通す。
- **本番 DB への書き込みは、アプリケーションコード（Route Handler → `PrismaBookRecordRepository`）経由に限る。** それ以外の経路（手元での CLI 実行・手打ち SQL・Supabase の管理コンソール・MCP）を通常運用に組み込まない。
- **スキーマ変更はこのリポジトリから適用しない。** テーブル定義の反映は別プロジェクト側で実施し、完了後に `cd front && pnpm prisma:pull` で写しを同期する（`database.md`「スキーマ同期フロー」）。**このリポジトリに正規の本番マイグレーション適用コマンドは存在しない。**
- **接続先は毎回明示的に確認する。** 「たぶんローカルを向いている」で破壊的操作を実行しない。実行前に接続先ホスト・プロジェクト名を出力して確認する。
- **既定は read-only。** 書き込み権限は必要な操作の直前にだけ与える。参照用の接続には読み取り専用ロールを使う。
- **本番の接続情報をローカルの既定環境変数に常駐させない。** 本番の `DATABASE_URL` は `front/.env.local` に閉じ、テストが暗黙に拾わないようにする（テスト側の接続先は `TEST_DATABASE_URL`。`testing.md` 参照）。
- **復旧手段を先に確認する。** バックアップ / PITR が有効で、直近の復旧ポイントが分かっている状態でのみ、書き換えを伴う操作を許可する。

## 環境の分離（本番を触らずに済む状態を先に作る）

書き換えを伴う作業には、**本番とは別の DB** を用意する。用途ごとに使い分ける。

**本プロジェクトは常設の非本番 Supabase 環境を持たない**（2026-08-22 決定・#76）。Supabase プロジェクトは本番 1 件のみで、開発用の別プロジェクトも常設ブランチ環境も作らない。単一ユーザー MVP であり、**下表のとおりローカルの使い捨てコンテナでほぼ全ての検証が成立する**ため、常設環境の費用に見合わないと判断した。

| 用途 | 使う環境 | 備考 |
|---|---|---|
| ローカル開発 | `local` ドライバ（`NEXT_PUBLIC_REPOSITORY_DRIVER=local`） | localStorage で完結し Supabase に接続しない |
| IT / E2E・Prisma / SQL / Route Handler の検証 | ローカルのコンテナ DB（`docker compose -f docker-compose.test.yml up -d --wait`） | 接続先ガードは `testing.md`「テスト用 DB の接続先（破壊防止）」を参照 |
| RLS ポリシー・Supabase Auth の実挙動の検証 | **未整備**（下記「把握したうえで残しているリスク」） | Prisma は DB オーナー接続のため RLS をバイパスする |
| どうしても実 Supabase が要る検証 | **その都度ブランチを作成し、使い終わったら破棄する** | 常設しない。作成・破棄はユーザーが行う |

- **本番と非本番は、接続情報を別の変数・別の保管場所で管理する。** 同じ変数名を環境で切り替える運用は、取り違えを検知できないため避ける。
- 非本番環境に**本番データをコピーしない**。必要な場合は個人情報をマスキング・匿名化したうえで持ち込む。
- **常設の非本番環境が無いことを、本番で作業してよい理由にしない。** まずローカルのコンテナ DB で成立しないかを検討し、それでも実 Supabase が要るなら**一時ブランチの作成を提案する**。本番を対象にするのは例外手順を通した場合に限る。

### 把握したうえで残しているリスク

上表の判断は、以下を**認識したうえで**下している。忘れて「検証済み」と誤認しないために明記する。

- **RLS ポリシーの正が本番 DB の中にしか無い。** `docs/06-security-specification.md` §7 に表としての記述はあるが、再現可能な SQL がリポジトリに無く、記述と実物の一致を機械的に確認できない。
- **Prisma は RLS をバイパスするため、IT が全件 green でも RLS は検証されていない。**

いずれも #81 で対応する。**非本番環境を置かない判断は、この 2 点を塞ぐこととセットで成立する。**

## 禁止する操作（本番接続先に対して）

- スキーマの破壊的再作成・リセット（`prisma db push` / `prisma migrate reset` / `prisma migrate deploy`）
- `TRUNCATE` / `DROP` / 条件なしの `DELETE` / 条件なしの一括 `UPDATE`
- テスト・シードスクリプトの実行（seed は既存データを削除する前提で書かれていることが多い）
- マイグレーションファイルを介さない、コンソール・CLI での直接スキーマ変更

これらが必要になった場合は、後述の「例外手順」を通す。ルールを黙って迂回しない。

## AI エージェント（Claude Code / Codex / MCP）に対する制約

自動化されたエージェントは**接続先を確認せずに操作を完了できてしまう**ため、人間より強い制約を課す。

- **本番プロジェクトに対する Supabase MCP の書き込み系ツール（`execute_sql` / `apply_migration` / `pause_project` / `restore_project` / `delete_branch` 等）を実行しない。** 参照系（`list_tables` / `list_migrations` / `query_logs` / `get_advisors`）に留める。`execute_sql` は `SELECT` であっても本番に対しては使わない。
- 書き込みが必要な場合は、**まず非本番環境（開発用プロジェクト / ブランチ環境 / ローカルの使い捨てコンテナ）を対象にできないか検討し、そちらへ振り替える。**
- それでも本番への書き込みが必要な場合は、**実行前に「接続先（プロジェクト名 / ホスト）」と「実行する SQL」を提示し、ユーザーの明示承認を得る。** 承認は 1 操作ごとに取り、以前の承認を次の操作に流用しない。
- **エラーの回避策として接続先を変更しない。** 「ローカル DB に繋がらないから本番を使う」「環境変数を手で書き換えて通す」は禁止。原因を報告して止まる。
- スキーマ変更は**別プロジェクト側の作業**であり、エージェントがこのリポジトリから本番へ適用しない。

## 例外手順（本番データの修正が避けられない場合の最終手段）

0. **非本番環境で代替できないことを確認する**（できるなら本番を対象にしない）。そのうえで、同じ操作を非本番環境で先に実行し、結果を確かめる
1. 目的・影響範囲・対象件数を事前に書き出す（issue / PR に残す）
2. **dry-run を先に実行**し、対象件数と対象レコードを確認する
3. バックアップ / PITR の復旧ポイントを確認する
4. **冪等なスクリプト**として実装し、レビューを受ける（アドホックな手打ち SQL にしない）
5. 実行時は接続先を明示表示し、トランザクションで囲む。想定件数と乖離したらロールバックする
6. 実行結果（対象件数・所要時間・異常の有無）を記録に残す

## DB 以外の本番リソース

同じ原則を、破壊・不可逆な副作用を持つ他の本番リソースにも適用する。

- オブジェクトストレージの削除・上書き
- メール / 通知の一斉送信（宛先を本番ユーザーに向けた実行）
- 決済・課金 API の実行（テスト用キーとの取り違え）
- キュー・ジョブの一括削除、外部 SaaS の一括更新

いずれも**接続先・宛先・キーの種別を allowlist で検証**し、本番を指していたら実行前に失敗させる。
