# Vercel デプロイ制御ルール

Vercel の Git 連携は **GitHub Actions を経由せず push を直接拾う**ため、`.claude/rules/github-actions.md` の変更範囲判定では**デプロイを制御できない**。制御は **`vercel.json` 側で行う**。

## 結論

| 設定 | 結論 | 理由 |
|---|---|---|
| `git.deploymentEnabled` | **入れる** | 失敗しても即座に気づける（プレビュー URL が出ない／本番が更新されない）。1 行で戻せる |
| `ignoreCommand` | **入れない** | 失敗が静かに起きる。得るものが小さく、失うものが大きい |

**この領域の失敗は「ビルド失敗」として現れない。** デプロイが走らないミスは「無いものが見えない」形で発覚するが、ビルドスキップのミスは「**古いものが正常に見えている**」形で潜伏する。この非対称性が判断の軸になる。

**パスによる実行制御は、本番状態を壊さない CI 側（`github-actions.md`）に寄せる。**

## vercel.json の配置

- Vercel プロジェクトの **Root Directory 直下**に置く。本プロジェクトは Root Directory が `front/` のため **`front/vercel.json`**（リポジトリ直下ではない）。
- 先頭に `"$schema": "https://openapi.vercel.sh/vercel.json"` を宣言する。

## 1. ブランチ単位のデプロイ制御（`git.deploymentEnabled`）— 入れる

**`deploymentEnabled` は許可リストではなく拒否リストである。** 公式ドキュメントに `Unspecified branches default to true` と明記されており、**列挙しなかったブランチはデプロイが発火する**。

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "git": {
    "deploymentEnabled": {
      "**": false,
      "main": true
    }
  }
}
```

- **`{"main": true}` だけ書いても何も止まらない。** 全ブランチの Preview デプロイが走り続ける。**設定したつもりで効いていない**という、最も気づきにくい失敗になる。
- **まず `"**": false` で全ブランチを止め、許可するブランチを `true` で上書きする**。複数パターンにマッチした場合、**1 つでも `true` があればデプロイされる**（OR 判定。記述順や最長一致ではない）。
- ワイルドカードは **minimatch** で評価され、**`*` は `/` を跨がない**。本プロジェクトは `feat/xxx` `chore/xxx` のようにスラッシュを含むブランチ名を使うため、**`"*": false` では素通りする**。必ず `**` を使う。
- Preview 環境が必要な場合は対象ブランチを**明示的に追加**する（例: `"release/**": true`）。「とりあえず全ブランチ許可」にしない。
- `"main": false` のように**本番ブランチを無効化しない**（デプロイ手段が失われる）。
- **変更後は必ず両方向を確認する**: docs のみのブランチを push して Preview が発火しないこと、および **main へマージして本番デプロイが発火すること**。拒否リストの書き方を誤ると本番が止まる。

## 2. ビルドスキップ（`ignoreCommand`）— 原則として入れない

### 2.1 なぜ入れないか

| 観点 | 内容 |
|---|---|
| 得るもの | docs のみの main マージでビルド 1〜2 分の節約 |
| 失うもの | 判定を誤ると**本番が静かに古くなる**（デプロイ履歴は緑のまま） |
| 安全に運用するコスト | 本番稼働 SHA の監視実装が必要。**その手間だけで節約分を超える** |

`HEAD^` 基準の欠陥（後述 2.3）は設計で直せるが、**失敗の観測可能性が非対称**である性質は設計を直しても消えない。

**本プロジェクトは実際に本番凍結を起こした。** `front/scripts/vercel-ignore-docs.sh` が `git diff` の失敗を `|| true` で握り潰し、空の変更リストを「変更なし」と解釈して `exit 0`（スキップ）を返していた。Vercel は既定で shallow clone するため基準 SHA がローカルに無く、この経路に入っていた。結果、**PR #26 以降の本番デプロイが全てスキップされ、コード変更を含む #65 / #67 / #69 が本番へ反映されなかった**。

### 2.2 それでも導入する場合の最低条件

以下 4 点を**すべて**満たせないなら入れない。1 つでも欠けるなら入れない。

1. 比較基準に **`VERCEL_GIT_PREVIOUS_SHA`**（前回"成功した"デプロイの SHA）を使う。`HEAD^` を使わない
2. **基準が取れない・基準コミットがローカルに存在しない場合は必ず非 0（＝ビルド実行）**。`git cat-file -e "${BASE}^{commit}"` で存在確認し、**`|| true` で失敗を握り潰さない**
3. 判定ロジックを **`vercel.json` の一行文字列ではなくスクリプトへ切り出す**（JSON とシェルの二重エスケープでローカル検証できないため）
4. **本番稼働 SHA の監視**を用意する（`VERCEL_GIT_COMMIT_SHA` をヘルスチェック等で公開し、main の HEAD と突き合わせる）

**終了コードの規約（直感と逆）**: `0` = スキップ / 非 0 = 実行。`git diff --quiet` は差分なしで `0` を返すため、「除外パス以外に差分がなければ `0` → スキップ」と読む。

### 2.3 `HEAD^` を基準にしない理由

| 失敗モード | 何が起きるか |
|---|---|
| **スキップの累積** | 一度スキップしたコミットの変更は未デプロイのまま、次回の判定窓 `HEAD^..HEAD` の外に出る。ずれは自己修復せず本番が凍結する |
| **マージコミット** | `HEAD^` は第一親（main の旧先端）を指すため、判定窓が「その 1 マージ分」に限定される |
| **複数コミットの同時反映** | Rebase and merge 等で N コミットが一度に載ると先頭 1 コミットしか評価されず、後方のアプリ変更が恒久的にこぼれる |

### 2.4 監視

- スキップされたデプロイは Vercel ダッシュボードで `Ignored`（API 上は `CANCELED`）表示になる。**アプリコードを変更した push が `Ignored` になっていたら判定ロジックのバグ**。
- **本番が最新コミットと一致しているかを定期的に突き合わせる。** ビルドスキップの失敗はビルド失敗として現れないため、能動的に見ないと気づけない。

## GitHub Actions との役割分担（重複させない）

| 観点 | 担当 |
|---|---|
| Vercel のデプロイをどのブランチで走らせるか | 本ファイル ＝ `front/vercel.json` の `git.deploymentEnabled` |
| **パスによる実行制御**（変更内容に応じた絞り込み） | **`github-actions.md`** ＝ `.github/workflows/ci.yml`。本番状態を壊さない側に寄せる |

- GitHub Actions から Vercel CLI でデプロイする構成へ移行した場合は、Vercel ダッシュボードで Git 連携を無効化し、発火制御を `github-actions.md` に一本化する。

## レビュー観点

- `deploymentEnabled` が **`"**": false` から始まっているか**（`{"main": true}` だけになっていないか）。
- **`ignoreCommand` が追加されていないか。** 追加する場合は §2.2 の 4 条件をすべて満たしているか。
- 判定が「判定不能 → スキップ」に倒れていないか（`|| true` で失敗を握り潰していないか）。
