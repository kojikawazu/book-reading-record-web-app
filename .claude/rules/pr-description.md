# PR 本文（初回コメント）の必須セクション

PR の初回コメント（PR 本文）は、レビュアーが**差分を読む前に判断材料を揃えられる**状態にする。変更種別ごとに必須セクションを固定し、省略しない。

## 共通ルール

- **変更種別を最初に宣言する**: `バグ修正` / `仕様変更` / `仕様追加` / `新規開発` のいずれかを本文冒頭に書く。複数にまたがる場合は主たる種別を選び、従の内容は「概要」に書く（1 PR に複数種別を詰め込まない方が望ましい）。
- **セクションは省略しない**: 該当がない場合も見出しを残し、`なし（理由）` と書く。空欄・見出しごと削除は不可。
- **原因欄に対処を書かない**: 「原因」は事象が起きたメカニズム、「方針」は直し方。`〇〇を修正した` は原因ではない。
- **受け入れ基準は検証可能な条件で書く**: 「正しく動く」ではなく「〇〇の状態で △△ すると □□ になる」と、レビュアーが再現・確認できる粒度で書く。
- **関連 issue は必ず参照する**: `Closes #<番号>`（バグ修正は `Fixes #<番号>`）を書く。運用の詳細は `github-issue.md` を正本とする。
- **差分から読めることを繰り返さない**: ファイル一覧の羅列ではなく、**なぜ**そう変えたかを書く。
- **スコープ外とした判断を明示する**: 気づいたうえで今回やらないと決めたことは、**理由（別 issue に切った / 影響が大きい / 別 PR が適切）まで含めて**「概要」または該当セクションに書く。書かないとレビュアーには「見落とし」と区別がつかず、同じ議論を後から必ずやることになる。既存ルールに反する状態を承知で残した場合は、**どのルールのどの項目か**を書く（例:「`frontend.md` はバリデーションの単一定義を求めているが現状は二重定義。統合は別 PR の範囲」）。

## 全種別で必須のセクション

| セクション | 書く内容 |
|---|---|
| 変更種別 | バグ修正 / 仕様変更 / 仕様追加 / 新規開発 のいずれか |
| 概要 | 何を変えたかを 1〜3 行で。レビュアーが最初に読む要約 |
| 関連 issue | `Closes #<番号>` / `Fixes #<番号>` |
| 受け入れ基準 | この PR が満たすべき条件をチェックリストで（検証可能な粒度） |
| テスト | 追加・修正したテストと、その観点。手動確認をした場合は手順と結果 |
| ドキュメント | 更新したドキュメント。不要と判断した場合はその理由（`documentation.md` の完了条件） |

### 本プロジェクトでの「テスト」欄の書き方

本プロジェクトは UT / IT / E2E の 3 層構成（`testing.md`）のため、**どの層で何を担保したかを層ごとに書く**。「テストを追加した」だけでは、実 DB でしか確認できない観点がモックで済まされていないかを判断できない。

- 各層の実行結果（件数・pass/fail）を書く。IT を実行した場合は**接続先ホスト**も書く（`localhost:5433` であること。`testing.md` のテスト DB 接続先ガード）
- 実行しなかった層がある場合は、その理由を書く（「該当なし」で済ませない）
- 既存テストを変更した場合は、**仕様変更に伴う期待値の更新なのか、実装に合わせた妥協なのか**を明記する。後者は `testing.md`「テストが失敗したら実装を修正する」に反するため、レビューで必ず問われる

## 種別ごとの追加セクション

### バグ修正

| セクション | 書く内容 |
|---|---|
| 事象 | 再現手順 / 期待する挙動 / 実際の挙動。影響範囲（対象ユーザー・データ・期間）も書く |
| 原因 | 根本原因。「どのコードのどの条件で」何が起きたか。表層の症状で止めない |
| 修正方針 | 原因に対してどう手を入れたか。対症療法を選んだ場合はその理由と恒久対応の予定 |
| 再発防止 | 同じ原因を再発させない手立て（回帰テスト・型・ガード・Lint ルール等）。テスト追加が主なら「テスト」と重複させず参照でよい |

### 仕様変更

| セクション | 書く内容 |
|---|---|
| 変更理由 | なぜ既存仕様を変えるのか（要求・課題・意思決定の出どころ） |
| 変更前 / 変更後 | 既存仕様と新仕様を対比で示す（表・箇条書き） |
| 影響範囲 | 影響を受ける機能・API・画面・データ。**後方互換の有無**を明示する |
| 移行手順 | 破壊的変更がある場合の移行方法（データ移行・段階リリース・フラグ・告知）。不要なら「なし（後方互換のため）」 |

**本プロジェクトでの注意**: `local` / `supabase` の 2 ドライバがあるため、影響範囲には**両ドライバでの挙動**を書く（`frontend.md`「両実装を更新する」）。片方だけ確認した場合はその旨を明記する。既存データへの影響がある場合は、**`schema.prisma` の変更を伴うか**も書く（伴うなら別プロジェクト側の作業が先に立つ — `database.md`）。

### 仕様追加

| セクション | 書く内容 |
|---|---|
| 背景・目的 | なぜこの機能を足すのか。解決する課題 |
| 追加仕様 | 追加した挙動の仕様（入力・出力・条件・エラー時の扱い） |
| 既存への影響 | 既存機能を壊していないことの根拠（触った共通処理・DB スキーマ・権限）。非破壊なら「追加のみ」と根拠を書く |

### 新規開発

| セクション | 書く内容 |
|---|---|
| 背景・目的 | 何のために作るのか。達成したいこと |
| スコープ | **含むもの / 含まないもの**を対で書く。次以降の PR に回した範囲を明示する |
| 設計方針 | 採用した構成・レイヤ分割・主要なライブラリ選定 |
| 設計判断 | 迷った点と選んだ理由（トレードオフ）。レビューで議論してほしい箇所 |
| 残課題 | 既知の未対応・TODO・後続 issue へのリンク |

## PR テンプレートとの関係

`.github/PULL_REQUEST_TEMPLATE/` に種別別のテンプレートを置くが、**必須セクションの正本は本ファイル**とする。テンプレートは本ファイルの見出しを写した骨格であり、両者が食い違った場合は本ファイルに合わせてテンプレートを直す。

**ディレクトリ形式のテンプレートは自動適用されない。** 単一ファイルの `.github/pull_request_template.md` と違い、`PULL_REQUEST_TEMPLATE/`（複数形ディレクトリ）は URL に `?template=<ファイル名>` を付けたときだけ適用される。したがって本プロジェクトでは、テンプレートは以下の 2 用途で使う。

1. `/pr-create`（`pr-create` スキル）が種別を判定し、該当ファイルを骨格として本文を組み立てて `--body` で渡す
2. GitHub UI から手動で PR を作る場合に、`?template=spec-change.md` のように明示的に選ぶ

**単一ファイルの `pull_request_template.md` は置かない。** 置くと全 PR に同じ骨格が挿入され、種別ごとにセクションを変える本ルールと衝突するため。

## 関連ルールとの分担（重複させない）

| 観点 | 担当ルールファイル |
|---|---|
| PR 本文に何を書くか（本ファイル） | `pr-description.md` |
| issue の起票単位・`Closes #` の運用・サブ issue | `github-issue.md` |
| ブランチ命名・GitHub Flow・push 禁止物 | `git.md` |
| ドキュメント更新の完了条件（影響マップ） | `documentation.md` |
| レビュー前のセルフチェック | `quality-gate.md` |
| テスト層の分類・接続先ガード | `testing.md` |
