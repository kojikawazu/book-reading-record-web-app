# 静的解析の運用

使用するツールは各言語のコーディング規約（`typescript.md`）で定める。本ルールは**どう運用するか**を定める。

## 役割分担（重ねない）

| 種類 | 役割 | 議論の対象 |
|---|---|---|
| **Formatter** | 見た目（インデント・改行・引用符）を機械的に統一する | **しない**。デフォルト設定に従う |
| **Linter** | バグの温床・危険なパターンを検出する | ルールの追加・除外のみ議論する |
| **型チェッカ** | 型の不整合を検出する | しない |

- **見た目に関する Linter ルールを有効にしない**。Formatter と競合し、直しても直らないエラーが発生する（TypeScript は `eslint-config-prettier` で無効化する）。
- **フォーマットの好みを議論しない・レビューで指摘しない**。Formatter の出力が正である。フォーマット指摘が出る状態なら、それは CI の設定不足である。

## CI で必須にする

- **Linter・Formatter・型チェックはすべて CI で実行し、違反があればマージをブロックする**。ローカル任意実行にしない。
- **警告（warning）を放置しない**。「警告は出るが動く」状態が常態化すると、新しい警告が埋もれて検出装置として機能しなくなる。**警告ゼロを維持**し、守れないルールは有効にしない（`error` にするか、無効にするかの二択）。
- Formatter は**差分ゼロを検証**する（`--check` / `--test` 系）。CI がコードを自動整形してコミットし返す運用にしない。
- 型チェックは**ビルドとは別に明示実行**する（TypeScript の `tsc --noEmit` 等）。バンドラの型スキップ設定で見逃さないため。

## 抑制コメントの扱い

`eslint-disable` / `@ts-expect-error` などの抑制は、**例外的な手段**として扱う。

- **理由をコメントで必ず書く**。「なぜこのルールを守れないのか」「いつ解消できるのか」を書く。理由のない抑制は差し戻す。
- **範囲を最小にする**。ファイル全体ではなく**該当行のみ**を抑制する。ファイル先頭での一括無効化をしない。
- **抑制するルールを明示する**（`eslint-disable-next-line no-console` のように**ルール名を書く**）。ルール名なしの全ルール抑制をしない。
- `@ts-ignore` ではなく **`@ts-expect-error` を使う**（問題が解消したとき「不要な抑制」として検出されるため、抑制が残り続けない）。
- 同じ抑制が**何箇所にも増えたらルール設定自体を見直す**。プロジェクトの実態に合っていないルールを、抑制コメントで回し続けない。

## ルール設定の変更

- **ルールの追加・除外はプロジェクト全体の合意で行い、設定ファイルに理由をコメントで残す**。個人の好みで一時的に緩めない。
- 既存プロジェクトへ厳しいルールを導入して大量の違反が出る場合、**一括抑制せず段階導入する**（対象ディレクトリを限定する、新規コードのみ対象にする、期限を決めて解消する）。
- 設定ファイル（`front/eslint.config.mjs` 等）は**コミット対象**。ローカル固有設定に依存しない。

## エディタ・コミット時

- **エディタの保存時フォーマットを有効にする**（CI で落ちる前に手元で解決する）。
- pre-commit フックを使う場合は**高速なもの（変更ファイルのみの format / lint）に限定**する。テストや全体型チェックを含めるとコミットが重くなり、`--no-verify` が常態化する。
- **フックは CI の代替にならない**。スキップ可能なため、最終的な担保は必ず CI に置く。

## レビュー観点

- 抑制コメントに理由が書かれているか。範囲・ルール名が最小限に絞られているか。
- Formatter が直すべき見た目をレビューで指摘していないか（＝設定不足のサイン）。
- 警告が出たまま放置されていないか。
